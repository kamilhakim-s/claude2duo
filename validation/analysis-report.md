# Prompt experiment — Stage 0/1 results and pre-Duo analysis

Date: 2026-07-12 · sample app: `sample-app/` (transfer-service) · packs generated at commit `b225393`

## Methodology and caveats — read first

- All five packs were generated by Claude (this session) following each prompt's spec
  faithfully, into `sample-app/docs/context-pack-v{1..5}/`. **Caveat:** the test protocol
  calls for a *fresh Claude Code session per prompt*; these were produced in one session,
  so variant independence is weaker than the real procedure. Structure/size/strategy
  differences are representative; before adopting the winner, the licensed developer
  should re-run that one prompt in a fresh session as the production baseline.
- v5's Phase B is spec-identical to prompt 1, so v5 was seeded from v1 and then the
  Phase C adversarial self-test was genuinely executed — 4 real defects were found and
  patched (see `context-pack-v5/SELF-TEST-REPORT.md`). This isolates exactly what the
  self-critique phase buys.
- One protocol-driven fix was applied to ALL five packs equally (keeps comparison fair):
  the original in-repo v1 prompt required "list which context files are now stale" after
  implementation — your test protocol's T3 scores it — and none of the five new prompts
  had inherited it. Added to every AI-WORKFLOW.md, and it should be added to the five
  prompt texts too (noted in Recommendations).

## Content-sufficiency preview of T1–T3 (proxy, not a Duo run)

Assessed by checking whether each pack *contains the information* Duo needs per task in
`prompts/test-protocol.md`. This predicts, it does not replace, the Duo runs.

| Task | v1 | v2 | v3 | v4 | v5 |
|---|---|---|---|---|---|
| T1 flow + rejection rules | ✔ full | ✔ full | ✔ full | ✔ full | ✔ full |
| T2 add `description` field | ⚠ gap: doesn't state the TWO `new Transfer(...)` sites nor positional-record blast radius — a plan from this pack alone likely misses one call site | ⚠ same gap (flow hints at two persists, but not construction) | ⚠ same gap; no constructor signatures | ✔ RECIPES R3 covers both call sites + record pitfall explicitly | ✔ patched in Phase C (defects 1–3) |
| T3 rule placement (>10,000 reject) | ✔ CONVENTIONS explicit | ✔ WORKING-HERE explicit | ✔ CONVENTIONS row explicit | ✔ R6 dedicated recipe incl. ordering pitfall | ✔ + ordering gotcha |

Key early finding: **the T2 trap separated the strategies exactly as designed.** Only the
cookbook (task-recipe) strategy surfaced the two-construction-sites pitfall on its own,
and the self-critique phase found it by testing. Reference-style packs (v1–v3) documented
*what exists* accurately but not *what a change touches*.

## Predicted ranking (to confirm/refute in Duo)

1. **v4 cookbook** — best change-planning support per token (~3.5k); recipes map 1:1 to
   how tasks are phrased. Risk: recipe set must fit the service; unusual tasks fall
   through to "no pattern — ask".
2. **v5 self-critique** — most complete; the self-test demonstrably caught real gaps.
   Cost: largest (~6.3k tokens) and the most expensive to generate/regenerate.
3. **v3 compact** — everything needed for Q&A at 1/4 the tokens of v5; best long-session
   headroom. Risk: dense notation may degrade Duo's parsing — watch T1 closely.
4. **v2 persona** — readable and honest, good for humans; less mechanical support for
   change planning (no recipes, no constructor detail).
5. **v1 spec** — solid but strictly dominated by v5 (same structure + patched gaps) at
   only ~1k fewer tokens.

## What to run in GitLab Duo (the deciding stage)

Per variant, fresh Duo session in IntelliJ/VS Code, attach the pack per its INDEX/
MANIFEST, then per `prompts/test-protocol.md` + `validation/validation-plan.md` Stage 3:

1. T1 comprehension question (score 0–2, hallucination check).
2. T2 description-field task via the workflow: confirm plan-before-code, affected-files
   table, both `Transfer` call sites present in the plan.
3. T3 the >10,000 rule with the layering trap.
4. Workflow gate checks W5–W9: refine bumps version; "give me the code" before approval
   is refused; step 1 code is paste-ready; fake error fixes only step 1; staleness list
   appears after the final step.
5. Record everything in `validation/scoresheet.csv` (Stage 1 rows are pre-filled).

Practical notes: attach ALL files of a variant (packs are small); if Duo truncates the
v5 pack, that is itself a scoring result (size is a criterion). The
`validation/duo_chat_runner.py` script can automate the Q&A stage from inside your
network if your GitLab exposes the `aiAction` GraphQL mutation; the workflow-gate stage
is conversational and better done manually either way.

## Recommendations so far

- Whatever wins, fold in: the **staleness step** (all prompts), **R3-style "both call
  sites" recipes** (v4's key advantage), and the **self-test phase** (v5's) — they are
  composable: a likely final production prompt is *v4's structure + v5's Phase C +
  v3's size discipline*.
- Update the five prompt files in `prompts/` with the staleness-step line before the
  fresh-session re-runs, so regenerated packs keep it.
